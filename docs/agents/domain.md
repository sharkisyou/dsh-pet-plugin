# 领域文档

本文件说明各工程技能在探索代码库时应如何消费本仓库的领域文档。

## 探索前先阅读

- 根目录的 **`CONTEXT-MAP.md`** —— 它指向每个上下文的 `CONTEXT.md`。阅读与当前主题相关的每一份。
- **`docs/adr/`** —— 阅读与即将动手区域相关的 ADR。多上下文仓库中，还需检查各插件目录下的 `docs/adr/`（插件内决策）。

如果这些文件不存在，**静默继续**。不要标记缺失，也不要主动建议创建。`/domain-modeling` 技能（通过 `/grill-with-docs` 与 `/improve-codebase-architecture` 触达）会在术语或决策真正落地时按需创建它们。

## 文件结构

多上下文仓库（本仓库：DeepSeek Harness 插件仓库，可能有多个插件）：

```
/
├── CONTEXT-MAP.md                     ← 指向每个插件的 CONTEXT.md
├── docs/adr/                          ← 系统级决策（跨插件）
└── plugins/                           ← 每个插件一个目录（实际目录名以仓库为准，如 packages/）
    ├── <plugin-a>/
    │   ├── CONTEXT.md                 ← 插件 A 的上下文 / 词汇表
    │   └── docs/adr/                  ← 插件 A 内部决策
    └── <plugin-b>/
        ├── CONTEXT.md
        └── docs/adr/
```

单上下文仓库（只有一个插件时也适用）：

```
/
├── CONTEXT.md
├── docs/adr/
│   ├── 0001-xxx.md
│   └── 0002-xxx.md
└── src/
```

## 使用词汇表中的术语

当你的输出命名某个领域概念时（issue 标题、重构提案、假设、测试名），请使用 `CONTEXT.md` 中定义的术语，不要漂移到词汇表明确规避的同义词。

如果所需概念尚未进入词汇表，这是一个信号 —— 要么你在发明项目不用的语言（请重新考虑），要么确实存在空缺（记录下来，交给 `/domain-modeling`）。

## 标记 ADR 冲突

如果你的输出与既有 ADR 相矛盾，请明确指出来，而不是默默覆盖：

> _与 ADR-0007（xx）冲突 —— 但值得重新审视，因为……_
